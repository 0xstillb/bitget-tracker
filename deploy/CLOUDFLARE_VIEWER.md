# Cloudflare Access for the Pi Viewer

This deployment publishes only the read-only Pi Viewer. The Core and login
worker must never be Cloudflare Tunnel ingress services and must never receive
public DNS records. The Pi continues to reach Core only over Tailscale.

## 1. Create and protect the hostname

Create a named Cloudflare Tunnel and route one hostname, such as
`viewer.example.com`, to it. Copy `cloudflared-config.example.yml` to
`/etc/cloudflared/config.yml`, replace the tunnel UUID and hostname, and keep
the downloaded credentials JSON readable only by root/cloudflared. Do not put
a tunnel token or credentials JSON in `viewer.env` or this repository.

Before sharing the hostname, create a Cloudflare Access self-hosted application
for the exact hostname. Use deny by default: add only the intended identity
provider users/groups to an Allow policy and keep every bypass policy disabled.
Use a short session duration and require MFA at the identity provider.

The final ingress rule must remain `http_status:404`; it prevents unmatched
hostnames from falling through to another local service. The only origin in the
configuration is `http://127.0.0.1:8080`.

## 2. Restrict the Pi origin

`cloudflared` makes outbound connections, so configure no inbound port-forward
on the router. Keep TCP 8080 reachable only from loopback and the trusted LAN
used by the ESP32. Never allow it from a WAN interface. Example UFW policy,
after replacing the example subnet and first confirming the Pi's SSH rule:

```sh
sudo ufw default deny incoming
sudo ufw allow from 192.168.1.0/24 to any port 8080 proto tcp comment 'Viewer LAN only'
sudo ufw deny 8080/tcp
```

The LAN allow must appear before the general deny. Confirm with
`sudo ufw status numbered`. Do not expose Core port 10000, browser debugging
ports, or worker process ports in UFW, the router, Cloudflare DNS, or Tunnel
ingress.

Install `cloudflared` from Cloudflare's signed package repository, validate the
configuration, then install/start its system service. Keep the Viewer systemd
unit and cache permissions from `PI_VIEWER.md`.

## 3. Manual validation on real infrastructure

These checks require the actual Cloudflare account, domain, Tunnel, and Pi:

1. With no Access session, request `https://viewer.example.com/` and confirm an
   Access login/denial page appears rather than Viewer content.
2. Sign in as an allowed identity and confirm `/`, `/api/v1/summary`, and
   `/api/v1/health` work while POST returns HTTP 405.
3. Confirm responses include `Cache-Control: no-store` and the CSP/security
   headers generated by `pi_viewer.py`.
4. Request an unconfigured hostname/path through the Tunnel and confirm the
   catch-all returns 404.
5. From outside the LAN, verify the Pi's public IP has no open inbound Viewer,
   Core, SSH, browser, or worker ports that were not explicitly intended.
6. Stop Core temporarily and confirm Viewer continues serving last-good cached
   data; then restore Core and confirm refresh recovery.

Local automated tests validate configuration shape and application headers,
but they cannot prove Cloudflare Access policy enforcement or the real firewall.
